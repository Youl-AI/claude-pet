# claude-pet 설계 문서

**작성일**: 2026-08-28
**상태**: 승인됨

## 1. 목적

Windows 화면 위를 자유롭게 돌아다니는 데스크톱 펫을 만든다. 펫은 Claude Code 세션에
연동되어, 세션이 시작되면 등장하고 모든 세션이 끝나면 사라진다. 펫은 Claude Code가
지금 무슨 일을 하는지 연기하고, **사람의 입력이 필요한 순간을 눈에 띄게 알린다.**

해결하려는 실제 문제는 두 가지다.

1. Claude Code가 응답을 마치고 사용자를 기다리는데 사용자가 눈치채지 못해 시간이 낭비된다.
2. 에이전트가 무슨 일을 하는지 터미널을 계속 들여다봐야 알 수 있다.

## 2. 최상위 제약: 방해 0

> **코딩 작업이 펫으로 인해 0.1도 방해받지 않아야 한다.**

이것은 성능 목표가 아니라 **설계 제약**이다. 다른 모든 요구사항보다 우선하며,
어떤 기능이든 이 제약과 충돌하면 그 기능을 버린다.

"방해"는 다음 여섯 가지를 모두 포함한다.

| 경로 | 내용 |
|---|---|
| 지연 | Claude Code의 도구 호출·프롬프트 처리가 느려지는 것 |
| 포커스 | 타이핑 중 창이 포커스를 가져가는 것 |
| 마우스 | 클릭이 펫에 가로막히는 것 |
| 자원 | CPU/GPU를 두고 빌드·테스트와 경쟁하는 것 |
| 파일 잠금 | 펫의 파일 접근이 Claude Code의 쓰기를 방해하는 것 |
| 화면 가림 | 읽고 있는 코드를 펫이 가리는 것 |

각 경로에 대한 대응은 6절에 기술한다.

## 3. 범위

### 1단계 (이 스펙의 대상)

- 화면 위를 배회하는 항상-최상위 투명 펫
- Claude Code 활동에 대한 반응 연기
- 사람 입력 필요 상태의 3단계 강조
- 세션 연동 생명주기 (등장/소멸)
- 코드로 생성한 스프라이트

### 2단계 (이후)

- 다른 창의 제목 표시줄 위를 걷는 Shimeji식 기어오르기.
  1단계에서 바닥 판정 로직을 인터페이스로 분리해 확장 여지만 남긴다.

### 하지 않는 것 (YAGNI)

- XP / 레벨 / 코스메틱 해금
- 마우스로 집어서 던지기 등 상호작용
- 펫 여러 마리
- 소리

## 4. 구성 요소

세 조각으로 나뉘며, 화면에 무언가를 그리는 것은 하나뿐이다.

### 4.1 `pet.exe` — WPF 애플리케이션

유일한 시각적 실체. .NET 10 (`net10.0-windows`), WPF.
내부는 두 층으로 엄격히 분리한다.

- **`PetCore`** — 순수 C# 클래스 라이브러리. 화면을 전혀 모른다.
  이벤트를 받아 `PetState`와 이동 목표만 산출한다.
  상태 머신, 세션 레지스트리, 워치독 판정, JSONL 파서가 모두 여기 있다.
  **xUnit으로 단위 테스트한다.**
- **`PetApp`** — WPF 창. `PetCore`의 산출물을 그리기만 한다. 자동 테스트하지 않는다.

경계 기준: `PetCore`는 픽셀·좌표계·윈도우 핸들을 모른다. 이 경계가 무너지면
테스트 불가능한 코드가 된다.

### 4.2 플러그인

훅 정의와 실행 파일만 담는다. 그림은 그리지 않는다.

```
claude-pet-plugin/
├── .claude-plugin/
│   └── plugin.json
├── hooks/
│   └── hooks.json
└── bin/
    └── pet.exe
```

경로 참조는 `${CLAUDE_PLUGIN_ROOT}`, 상태 저장은 `${CLAUDE_PLUGIN_DATA}`를 사용한다.
(둘 다 공식 문서에 명시된 변수다.)

### 4.3 `spritegen.py`

빌드 타임 전용 도구. Python으로 픽셀을 찍어 PNG 스프라이트 시트를 생성한다.
결과물은 저장소에 커밋한다. **런타임에는 절대 실행되지 않는다.**
외부 에셋 의존성과 라이선스 문제를 0으로 만들기 위한 선택이다.

## 5. 신호 경로

설계의 핵심 판단. 두 경로를 성격에 따라 나눈다.

### 5.1 훅 — 드문 상태 전이만

**남기는 훅은 셋뿐이며, 전부 `async: true`이고, 셋 다 사용자가 코딩 중일 때는
발생하지 않는다.**

| 훅 | 매처 | 시점 | 용도 |
|---|---|---|---|
| `SessionStart` | (없음) | 세션 시작·재개·clear·compact·fork | 펫 기동 + 세션 등록 |
| `Notification` | `permission_prompt`, `idle_prompt` | 권한 대기 / 60초 방치 | 사람 필요 신호 |
| `SessionEnd` | (없음) | 세션 종료 | 세션 해제 (힌트) |

`Notification`은 정의상 **사용자가 코딩하고 있지 않은 순간**에만 발생한다.
따라서 코딩을 방해할 수 없다. 이것이 "지연 0"의 근거다.

### 5.2 버리는 훅과 그 이유

| 훅 | 버리는 이유 |
|---|---|
| `PostToolUse` | 도구 호출마다 프로세스 생성. Windows에서 호출당 수십~수백 ms. 핫패스 직격. |
| `UserPromptSubmit` | 매 턴 발생. **프롬프트를 차단할 수 있고(exit 2) 타임아웃 30초.** 어긋나면 사용자 입력이 멈춘다. |
| `Stop` | 매 턴 발생. 프로세스 생성 비용이 핫패스에 붙는다. |

**결과: 도구를 호출하며 실제로 일하는 구간에 훅이 단 하나도 발생하지 않는다.**

### 5.3 트랜스크립트 tailing — 도구 단위 연기

`SessionStart` 훅이 stdin으로 넘겨주는 `transcript_path`를 펫이 직접 읽는다.
프로젝트 경로를 인코딩해서 추측할 필요가 없다.

모든 훅은 stdin JSON으로 `session_id`, `transcript_path`, `cwd`, `hook_event_name`을
공통으로 받는다. `SessionStart`는 추가로 `session_start_reason`,
`SessionEnd`는 `session_end_reason`을 받는다.

턴 종료는 트랜스크립트에서 추론한다 (5.4의 대가 참조).

### 5.4 받아들인 대가

`Stop` 훅을 버렸으므로 "턴이 끝났다"를 트랜스크립트에서 추론해야 하고,
**반응이 약 0.5초 늦어진다.** 펫의 반응 속도보다 코딩의 매끄러움이 우선이라는
판단에 따라 이 교환을 수용한다.

## 6. 방해 0의 구현

2절에서 나열한 여섯 경로에 대한 구체적 대응.

### 6.1 지연

5절 참조. 핫패스에 훅 0개. 트랜스크립트 감시는 이벤트 기반(`FileSystemWatcher`)으로
붙이고 폴링하지 않는다.

### 6.2 파일 잠금 (Windows 특유의 위험)

펫이 JSONL을 읽는 동안 Claude Code는 같은 파일에 쓴다.
**펫이 파일을 배타적으로 열면 Claude Code의 쓰기가 실패할 수 있다.**

규칙: 펫은 트랜스크립트를 **읽기 전용**으로,
반드시 `FileShare.ReadWrite | FileShare.Delete`로 연다.
어떤 잠금도 걸지 않는다. **이는 협상 대상이 아니며 테스트로 검증한다.**

### 6.3 포커스

세 가지를 모두 건다.

- `ShowActivated="False"`
- `WS_EX_NOACTIVATE` — 어떤 경우에도 포커스를 받지 않는다
- `WS_EX_TOOLWINDOW` — Alt+Tab 목록과 작업 표시줄에서 제외

### 6.4 마우스

`WS_EX_TRANSPARENT`로 클릭을 통과시킨다. 펫은 클릭을 가로막지 않는다.

### 6.5 자원

| 항목 | 예산 |
|---|---|
| 프레임레이트 | 12 fps 고정 (픽셀아트에 60fps는 과함) |
| 유휴 시 | 펫이 자거나 화면이 가려지면 렌더링 정지 |
| 프로세스 우선순위 | `BelowNormal` — 빌드·테스트와 CPU 경쟁하지 않음 |
| 유휴 CPU 목표 | 1% 미만 |

### 6.6 화면 가림

- 기본 활동 영역을 **주 모니터 작업 영역 하단 15% 이내의 가로 띠로 제한**한다.
  펫은 이 띠를 벗어나지 않으며, 세로 이동은 점프·앉기 같은 제자리 동작에 한정된다.
  성능이 0이어도 코드 한가운데를 걸어다니면 그것은 방해다.
  (`NeedsYou` 상태의 하단 중앙 이동도 이 띠 안에서 이루어진다.)
- 전체화면 앱(발표·영상·게임)이 포그라운드면 펫은 스스로 숨는다.

## 7. 생명주기 — SessionEnd를 믿지 않는다

### 7.1 SessionEnd가 권위가 될 수 없는 이유

1. SessionEnd 훅은 전체 1.5초 예산을 공유하며, 크래시나 터미널 강제 종료 시
   발동한다는 보장이 문서에 없다 → **좀비 프로세스가 남는다.**
2. **`/clear`와 `/compact`는 SessionEnd와 SessionStart를 연달아 발생시킨다.**
   순진하게 SessionEnd에서 죽이면 컴팩션마다 펫이 깜빡인다.

### 7.2 PID 하트비트가 권위

- `SessionStart` 훅이 `${CLAUDE_PLUGIN_DATA}/sessions/<session_id>.json`에
  자신의 PID와 `transcript_path`를 기록한다.
- 펫은 3초마다 등록된 PID들의 생존을 확인한다.
- 살아있는 세션이 0이 되고 유예 시간(10초)이 지나면 펫이 스스로 종료한다.
- `SessionEnd`는 그 파일을 지우는 **빠른 길일 뿐**이며, 실패해도 워치독이 정리한다.

이 구조는 `/clear`, `/compact`, 크래시, 터미널 강제 종료를 **모두 동일하게** 처리한다.

### 7.3 싱글턴 보장

named mutex로 중복 실행을 막는다. `SessionStart`가 몇 번 발생하든 펫은 한 마리만
존재한다. (공식 문서도 `resume`·`clear`를 넘어 프로세스를 유지하려면 매처 없는
`SessionStart` + 락 파일로 실행 상태를 추적하라고 명시한다.)

## 8. 여러 세션 / 여러 프로젝트

**펫은 한 마리다.** 프로젝트마다 고양이가 늘어나면 금방 성가셔진다.

- 세션이 여럿 등록되면 **가장 최근에 이벤트를 낸 세션**을 연기한다.
- **모든** 세션이 턴 종료 상태일 때 대기 신호를 강하게 낸다.

## 9. 상태와 동작

### 9.1 PetState

| 상태 | 동작 |
|---|---|
| `Idle` | 배회, 가끔 앉거나 졺 |
| `Reading` | 앉아서 두리번거림 |
| `Writing` | 무언가를 두드림 |
| `Running` | 빠르게 걸음 |
| `Error` | 놀람 |
| `NeedsYou` | 화면 하단 중앙으로 이동 + 명확히 구별되는 신호 |

### 9.2 NeedsYou의 3단계

| 단계 | 신호원 | 의미 |
|---|---|---|
| 1 | 트랜스크립트 턴 종료 추론 | "당신 차례입니다" |
| 2 | `Notification` / `permission_prompt` | "권한 대기로 막혔습니다" |
| 3 | `Notification` / `idle_prompt` (60초) | "아직 안 오셨네요" |

## 10. 테스트 전략

### 10.1 단위 테스트 (`PetCore`)

- 상태 머신: 이벤트 → 상태 전이
- 세션 레지스트리 등록/해제
- 워치독 판정: 가짜 PID를 죽였을 때 종료 결정이 나는가
- JSONL 파서

### 10.2 계약 테스트

- 가짜 훅 JSON을 stdin으로 넣었을 때 상태 디렉터리가 올바르게 기록되는가
- 훅 스크립트가 **어떤 입력에도 exit 0으로 끝나는가** (실패해도 삼킨다)

### 10.3 파일 잠금 테스트

- 펫이 트랜스크립트를 읽는 동안 다른 프로세스가 같은 파일에 쓸 수 있는가 (6.2 검증)

### 10.4 방해 0 측정 — 주장하지 않고 측정한다

**"방해되지 않습니다"는 말로는 부족하다. 숫자가 나오기 전까지 달성했다고 말하지 않는다.**

- 펫 ON/OFF 상태에서 동일한 도구 호출 묶음을 반복 실행해 지연 분포를 비교
- 유휴 시 CPU 점유율 기록
- 목표: 지연 차이가 측정 노이즈 범위 내, 유휴 CPU 1% 미만

### 10.5 수동 확인

GUI 렌더링(투명도 품질, 포커스 미탈취, 클릭 통과)은 수동으로 확인한다.

## 11. 검증된 사실 / 미검증 사항

### 검증됨

- WPF는 이 환경에서 `net10.0-windows`로 경고 0개·오류 0개 빌드 (실측)
- `${CLAUDE_PLUGIN_ROOT}`, `${CLAUDE_PLUGIN_DATA}` 공식 문서에 존재
- 모든 훅이 stdin으로 `session_id`, `transcript_path`, `cwd` 제공
- `Notification` 훅의 `permission_prompt`, `idle_prompt` 매처 존재
- 설치된 런타임: .NET 10.0.103, Node 24.13.1, Python 3.14.3, Git Bash

### 구현 초반에 확인할 것

1. **투명 최상위 창의 실제 렌더링 품질** — 창을 띄워봐야 안다. 최우선 확인 항목.
2. **기동 수단 비교** — `async: true` SessionStart 훅 vs `monitors/monitors.json`
   백그라운드 모니터. 어느 쪽이든 워치독이 권위라는 구조는 바뀌지 않는다.
3. **`PermissionRequest` 훅의 즉시성** — `Notification`/`permission_prompt`는 약 6초
   대기 후 발생한다. `PermissionRequest`가 더 즉각적이나 권한 결정에 관여하는 훅이라
   단순 신호용 사용 시 부작용이 없는지 확인이 필요하다.
   **기본값은 안전한 `Notification`이며, 검증되면 즉시성 있는 쪽으로 올린다.**
