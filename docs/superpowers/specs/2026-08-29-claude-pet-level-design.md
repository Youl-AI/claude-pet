# claude-pet 레벨 시스템 설계

**작성일**: 2026-08-29
**대상**: `claude-pet` v0.4.0
**전제**: 이 문서의 모든 수치는 실측값이다. 추정치를 쓴 곳은 그렇다고 밝힌다.

---

## 1. 무엇을 만드는가

펫이 사용자의 Claude 사용량에 따라 레벨을 올린다. 레벨은 펫 왼쪽 명패에 숫자로 표시된다.

**이 기능은 기존의 방해 0 제약(설계서 §2)을 조금도 완화하지 않는다.** 레벨 계산은 펫이 이미
읽고 있는 트랜스크립트에서 파생되며, Claude Code 쪽에 새로운 훅·새로운 I/O·새로운 지연을
만들지 않는다.

---

## 2. 지표: 비용(API 환산 달러)

### 2.1 토큰은 하나의 숫자가 아니다

트랜스크립트의 `message.usage`는 네 가지를 따로 센다. 실측(2026-07-21 ~ 08-28, 고유 API
호출 34,254건):

| 항목 | 값 | 전체 대비 |
|---|---|---|
| `input_tokens` | 172,438 | 0.002% |
| `cache_creation_input_tokens` | 160,048,381 | 2.06% |
| `cache_read_input_tokens` | 7,595,651,148 | **97.68%** |
| `output_tokens` | 19,880,011 | 0.26% |
| 합계 | 7,775,751,978 | |

### 2.2 raw 합계를 쓰지 않는 이유

`cache_read`가 전체의 97.7%다. Opus 5 기준 캐시 읽기는 $0.50/1M, output은 $25/1M —
**50배 차이인데 raw 합계는 둘을 똑같이 1로 센다.**

더 중요한 것은 캐시 읽기가 *일한 양*이 아니라는 점이다. 대화가 길어지면 매 턴 같은 컨텍스트를
다시 읽으므로 저절로 불어난다. 긴 세션 하나를 열어두고 아무 말이나 반복하면 레벨이 오른다.
**파밍 가능한 지표는 쓰지 않는다.**

### 2.3 채택: 모델별 단가를 적용한 비용

```
비용 = Σ (input × P_in + cache_write × P_in × 1.25
          + cache_read × P_in × 0.10 + output × P_out) / 1e6
```

단가($/1M):

| 모델 | input | output |
|---|---|---|
| `claude-opus-5` | 5.00 | 25.00 |
| `claude-opus-4-8` | 5.00 | 25.00 |
| `claude-fable-5` | 10.00 | 50.00 |
| `claude-sonnet-5` | 2.00 | 10.00 |
| `claude-haiku-4-5-20251001` | 1.00 | 5.00 |

캐시 쓰기 1.25배, 캐시 읽기 0.10배는 표준 배수다.

**가격표에 없는 모델은 `claude-opus-5` 단가로 계산한다.** 새 모델이 나와도 레벨이 멈추지
않게 하기 위해서다. 그 결과는 과대 또는 과소 추정일 수 있으나, 0으로 세는 것보다 낫다.

동일 데이터에 적용한 실측 결과:

```
claude-opus-5      19,122회   $3,413.04
claude-fable-5      6,462회   $2,691.17
claude-sonnet-5     7,504회     $194.04
claude-opus-4-8        83회      $17.82
claude-haiku-4-5    1,087회       $7.15
─────────────────────────────────────────
합계               34,258회   $6,323.23   (38일)
```

### 2.4 이것은 청구액이 아니다

Claude Code 사용자 대부분은 구독제이므로 이 값은 **API 환산액**이지 실제 지불액이 아니다.
Pro $20 구독자도 환산하면 월 수백 달러가 나온다.

**금액을 화면에 노출하지 않는다.** 명패에는 레벨 숫자만 표시한다. 만약 이후에 금액을
보여주게 되면 반드시 "API 환산 기준"이라고 명시해야 한다.

## 3. 데이터 출처와 중복 제거

### 3.1 출처

`~/.claude/projects/**/*.jsonl` — 펫이 이미 tail하는 파일이다. 각 assistant 메시지 줄에
`message.usage`, `message.model`, `timestamp`가 들어 있다.

실측 규모: 605개 파일, 1.1 GB, 13개 프로젝트 (38일치). 전량 스캔 **1.04초**.

### 3.2 중복이 57%다

```
usage 를 담은 줄:  79,492
고유 message.id :  34,252   ← 실제 API 호출 수
중복            :  45,240   (56.9%)
```

순진하게 더하면 **2.3배 부풀려진다.** 원인 두 가지를 실측으로 확인했다:

1. **응답 하나가 content 블록별로 여러 줄에 기록된다.** 같은 `message.id`, 다른 `uuid`,
   **동일한 usage**. 한 응답이 최대 10줄까지 나뉜 사례를 확인했다.
2. **worktree 복사본.** 같은 세션 파일이 두 프로젝트 디렉터리에 존재한다
   (`kkul-voca` 와 `kkul-voca--claude-worktrees-honeypot-backdrop`). 605개 중 2개.

### 3.3 제거 방식

**`message.id` 기준으로 한 번만 센다.** 두 원인 모두 이것으로 해결된다.

**id 집합은 파일 단위로만 들고 있다가 버린다.** 전체를 기억하면 34,254개 × 약 100 bytes =
3.4 MB이고 1년이면 40 MB가 된다 — 펫 전체가 75 MB인데 그 절반이 id 목록이 된다.

중복의 87%가 바로 다음 줄에서 발생하므로(간격 1) 파일 하나를 읽는 동안의 집합만으로 충분하다.
파일을 다 읽으면 집합을 버리고 **그 파일의 비용 하나만** 남긴다.

## 4. 레벨 곡선

### 4.1 3구간

```
구간 1   L 1~100     L = 1 + 13.6869 × ln(C / 3.61)
                     $3.61 ≤ C < $4,992

구간 2   L 100~1000  L = 100 + (C − 4,992) / 1,396.17
                     $4,992 ≤ C < $1,261,545

구간 3   L 1000~9999 L = 1000 + (C − 1,261,545) / 2,652.72
                     $1,261,545 ≤ C ≤ $25,133,372
```

`C < $3.61`이면 레벨 0(표시는 1로 클램프). `C = $3.61`에서 정확히 L1이다 — 경계는 포함이다.
`C > $25,133,372`이면 9999로 클램프.

정본 상수는 `a = 13.6869`, `C0 = 3.61`, `C2 = 4992`, `m3 = 1396.17` 넷이다. 나머지는 여기서
유도한다 — `m4 = m3 × 1.9 = 2652.72`, `C3 = C2 + 900 × m3 = 1,261,545`,
`C4 = C3 + 8999 × m4 = 25,133,372`. **구현은 유도값을 하드코딩하지 말고 계산해야 한다.**
그래야 나중에 `m3`만 바꿔도 경계가 따라온다.

### 4.2 왜 이 형태인가

**구간 1이 로그인 이유** — 초반에 자주 올라야 첫인상이 산다. 두 앵커를 통과하도록 풀었다:
`L30 = $30`(가벼운 사용자 한 달), `L100 = $4,992`(무거운 사용자 한 달).

**구간 2·3이 선형인 이유** — 로그로 두면 경계에서 레벨 값이 **뚝 떨어진다**. 구간 2는 레벨이
900개인데 비용 범위는 구간 1보다 좁아서, 로그로 맞추면 L100을 넘는 순간 레벨이 23배 싸진다.
한 달 걸려 L100을 찍자마자 L101부터 우수수 오르는 모양이 된다. 선형으로 두면 이 문제가 사라진다.

**모든 경계가 느려지는 방향으로만 움직인다:**

```
L99  $364.73  →  L100  $1,396.17   (3.83배 비싸짐)
L999 $1,396.17 → L1000 $2,652.72   (1.90배)
```

L100의 3.83배는 의도된 관문이다. 1년차에 사용자들이 L99~107에 모였다가 여기서부터 갈라진다.

### 4.3 페이스 (실측 사용량 기반)

| | 1주 | 1달 | 3달 | 6달 | 1년 | 2년 | 3년 | 5년 | 10년 |
|---|---|---|---|---|---|---|---|---|---|
| 가끔 Pro $400/월 | 45 | 65 | 80 | 89 | 99 | 103 | 106 | 113 | 131 |
| 주력 Pro $1.2k/월 | 60 | 80 | 95 | 101 | 106 | 117 | 127 | 148 | 200 |
| Max 보통 $3k/월 | 73 | 93 | 102 | 109 | 122 | 148 | 174 | 227 | 357 |
| 기준 사용자 $6.3k/월 | 80 | 99 | 107 | 117 | 139 | 183 | 226 | 313 | 531 |
| 헤비/팀 $15k/월 | 95 | 107 | 128 | 160 | 227 | 357 | 488 | 749 | 1212 |

L1000 도달: 헤비 7년 / 기준 21년 / Max 보통 35년 / 주력 Pro 86년.

레벨 1개 간격(L100~999): 헤비 3일 / 기준 8일 / Max 14일 / 주력 Pro 35일 / 가끔 Pro 3.4개월.

**대상 사용자 범위는 38배다** (월 $400 ~ $15,000). 플러그인을 찾아 설치하는 사람은 월 $30
수준의 가벼운 사용자가 아니라는 판단에 근거한다. 한 달 뒤 모두 L65~114에 모인다.

## 5. 표시

### 5.1 명패

펫 **왼쪽**에 단색 판을 두고 그 위에 숫자를 얹는다.

```
┌────┐
│ 47 │      ▄▄▄
└────┘      █ █
            ▘ ▘
```

| 항목 | 값 |
|---|---|
| 바탕 | `#121116` |
| 테두리 | `#EEEAE2` (1px) |
| 숫자 | `#FFFDF8` |
| 위치 | 펫 왼쪽 |
| 간격 | **6px** (판 오른쪽 끝 ↔ 펫 왼쪽 첫 픽셀 `LEFT_NUB_X0 = 4`) |
| 폭 | 가변 (자릿수에 따라) |
| 숫자 글꼴 | 3×5 픽셀, 자간 1px |

### 5.2 왜 명패인가

외곽선을 두른 맨 숫자는 *대부분의* 배경에서 읽히지만, 명패는 *모든* 배경에서 읽힌다. 뒤에
있는 것이 벽지가 아니라 우리가 그린 단색 판이기 때문이다.

색 후보 5종을 6개 배경(밝은 벽지·검정·하늘·잔디·회색·베이지)에서 렌더해 비교했다. 채택안이
유일하게 전부에서 동일하게 읽힌다 — **판이 명도의 양 극단을 다 갖고 있어서**, 밝은 배경에서는
검은 바탕이, 어두운 배경에서는 밝은 테두리가 분리를 만든다.

### 5.3 왜 왼쪽인가

빠직(`MARK_CENTER_X = 23`)과 물음표가 셀 오른쪽 위를 쓴다. 명패를 오른쪽이나 머리 위에 두면
`Blocked`·`YourTurn` 상태에서 겹친다.

### 5.4 왜 가변 폭인가

이 곡선에서 4자리는 사실상 도달 불가다(기준 사용자 21년). 고정 4자리로 두면 `0047`처럼
쓸모없는 앞자리 0을 수십 년 달고 다닌다. 자릿수가 늘어나는 순간(L99→100, L999→1000)은
평생 두 번뿐이고, 그 순간이 레벨업 이펙트와 겹치면 판이 넓어지는 것 자체가 연출이 된다.

## 6. 레벨업 이펙트

**8프레임, 12fps, 약 0.66초.** 몸통 실루엣에서 링이 바깥으로 퍼지며 사라진다. 명패도 2프레임
같이 반짝여 "저 숫자가 올랐다"를 연결한다.

**상태 애니메이션과 구조가 달라야 한다.** 상태(Idle/Blocked/…)는 계속 도는 루프지만 이펙트는
한 번 재생하고 끝나는 오버레이다. 따라서:

- 스프라이트 시트에 행을 추가하지 않는다. **별도 `flash.png`** (8프레임 × 32×32 = 256×32)
- 창에 `Image`를 하나 더 얹는다. 평소 `Collapsed`, 레벨업 때만 자기 프레임 카운터로 8프레임
  재생 후 다시 숨긴다
- 그래야 **어떤 상태 위에서든** 재생된다 — `Blocked`로 빨간 펫이 뛰는 중에 레벨업해도 얹힌다

**32×32 안에 들어간다.** 몸통이 `x 4..27`이라 좌우 4px 여유가 있고 링 3px이 맞는다. 위쪽은
15px 남는다. 아래쪽은 발이 바닥(`y=31`)에 붙어 있어 여유가 없으므로 링이 바닥에서 잘린다 —
빛이 바닥을 뚫지 않는 것이 오히려 자연스럽다.

**레벨업 감지는 이전 레벨을 상태 파일에 저장해야 한다.** 그러지 않으면 펫이 재시작될 때마다
다시 터지거나, 꺼져 있는 동안 오른 것을 놓친다.

## 7. 증분 상태 저장

### 7.1 문제

트랜스크립트는 38일에 1.1 GB로 자란다. 1년이면 13 GB다. 펫은 자주 재시작한다(세션 시작마다,
크래시 복구마다). 매번 전량 스캔은 곤란하고, 1초 폴링마다는 논외다.

### 7.2 상태 파일

`${CLAUDE_PLUGIN_DATA}/usage.json`:

```json
{
  "version": 1,
  "totalCostUsd": 6323.23,
  "level": 99,
  "files": {
    "<트랜스크립트 절대경로>": { "size": 20695541, "mtimeUnixMs": 1756400000000, "costUsd": 412.83 }
  }
}
```

기동 시 각 파일에 대해:

- `size`와 `mtime`이 저장된 값과 같으면 → **읽지 않는다.** 저장된 비용을 그대로 쓴다
- 다르거나 새 파일이면 → 그 파일만 전량 재스캔하고 항목을 갱신한다

605개 중 실제로 바뀌는 것은 현재 세션 파일 하나뿐이다.

**전량 재스캔을 쓰는 이유(부분 읽기를 하지 않는 이유)** — 중복 제거가 파일 전체를 봐야
정확하다. 같은 `message.id`가 최대 6,416줄 떨어져 다시 나오는 사례를 실측했으므로, 이어읽기로는
경계를 넘는 중복을 놓친다. 재스캔 대상은 보통 파일 하나이고 20 MB 파일이 약 20 ms다.

### 7.3 예산

| | |
|---|---|
| 상태 파일 크기 | 605줄 × 약 120 bytes ≈ **70 KB** |
| 상주 메모리 | 상태 딕셔너리 + 재스캔 중인 파일 하나의 id 집합 ≈ **1~2 MB** |
| 기동 시 비용 | 변경 파일만. 최초 1회는 전량 1.04초 |
| 폴링 중 비용 | 현재 세션 파일 하나의 크기·mtime 확인 |

### 7.4 갱신 주기

레벨은 **`PetHost`의 기존 1Hz 폴링에 얹지 않는다.** 매초 파일을 재스캔할 이유가 없다.
**30초에 한 번** 현재 세션 파일만 확인한다. 레벨 하나가 오르는 데 가장 빠른 사용자도 3일이
걸리므로 30초 지연은 무의미하다.

## 8. 방해 0 제약 준수

| 항목 | 판정 |
|---|---|
| 새 훅 | 없음 |
| Claude Code 프로세스에 주는 비용 | 없음 |
| 트랜스크립트 잠금 | 없음 (`FileShare.ReadWrite \| Delete` 유지) |
| 추가 상주 메모리 | 1~2 MB |
| 추가 CPU | 30초당 파일 하나 stat, 세션 파일 변경 시 재스캔 |
| 화면 추가 점유 | 명패 약 26×18 px |

레벨 스캔은 **렌더 스레드에서 하지 않는다.** 12fps 루프를 막으면 안 된다.

## 10. 미해결 (이 기능과 무관하게 남아 있는 것)

기존 감사에서 나온 항목들이며 이 스펙의 대상이 아니다:

- 고아 세션 파일 영구 잔존, `TouchedUnixMs` TTL 미구현
- 시계 역행 시 옛 알림 부활 (`nowMs - stamp <= StaleAfterMs` 단방향)
