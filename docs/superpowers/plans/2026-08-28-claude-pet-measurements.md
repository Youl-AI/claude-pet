## 1. 하네스 설계와 왜 그렇게 했는가

`bench/measure_overhead.ps1`은 브리프(`task-13-brief.md`)의 뼈대 스크립트를 다음 여섯
가지 요구 위에서 다시 짰다. 각 항목은 "숫자가 나오기 전까지 달성했다고 말하지 않는다"는
전제 아래, 숫자 자체가 거짓말을 하지 않도록 만들기 위한 것이다.

### 1.1 평균이 아니라 분포

모든 지연 측정은 median/P95/P99/min/max를 함께 보고한다(`Get-Distribution`). 평균은
사용자가 실제로 느끼는 끊김(꼬리 지연)을 감춘다 — 특히 P99가 중요한 이유는, 방해가
"가끔 한 번 크게 걸리는 것"으로 체감되기 때문이다.

### 1.2 ON/OFF 인터리브 + 무작위 순서

브리프 원안은 "OFF를 다 재고 나서 ON을 잰다"였다. 이 순서는 도중에 끼어드는 배경 부하
(Windows Update, 다른 앱의 순간적 디스크 I/O 등)를 통째로 펫 탓으로 돌리게 만든다.

이 하네스는 반복 횟수(`Iterations`=2000, `ComputeIterations`=2000)를 `Blocks`(기본 8,
ON 4 / OFF 4)개 블록으로 쪼개고, 블록 순서를 무작위로 섞는다
(`$labels | Sort-Object { Get-Random }`). 실제로 두 번 실행했을 때 나온 순서는 서로
달랐다 — `ON,ON,ON,OFF,ON,OFF,OFF,OFF`와 `OFF,OFF,OFF,ON,ON,OFF,ON,ON` — 고정된 교대가
아니라 매번 새로 섞인다는 뜻이다.

추가로, "재실행 시 부호가 뒤집힐 정도"(브리프 3단계 기준)를 사후에 재실행하지 않고도
가늠할 수 있도록, **조건 내부에서 블록 간 중앙값 변동폭**을 함께 보고한다. §2의 최종
실행에서: OFF 블록간 변동폭 0.0012ms, ON 블록간 변동폭 0.0013ms — 이 값이 조건 간
차이(0.0005ms)의 2배 이상이다. 실제로 이 문서를 준비하며 스크립트를 두 번 실행했는데,
**쓰기 지연 중앙값 차이의 부호가 두 실행 사이에 실제로 뒤집혔다**(1차 +0.0003ms → 2차
-0.0005ms) — 브리프가 요구한 통과 기준("재실행 시 부호가 뒤집힐 정도")을 문자 그대로
관측했다.

### 1.3 CPU는 코어당(%)과 시스템 전체(%)를 모두, 논리 프로세서 수와 함께 보고

기존에 기록된 "배회 중 2.21%"라는 값과 스펙의 "유휴 CPU 1% 미만"이 같은 기준으로 비교
가능한지 애매했다(리뷰에서 지적됨). 이 하네스는 `[Environment]::ProcessorCount`(이 머신은
12)를 항상 함께 출력하고, `PerCorePercent`(`TotalProcessorTime` 증가량 / 경과시간, 즉
코어 1개를 100%로 보는 값)와 `SystemWidePercent`(`PerCorePercent / 논리프로세서수`)를
둘 다 계산해 명시한다.

두 브리프의 기존 기록과 스펙 문구("배회 중 2.21%", "유휴 CPU 1% 미만")는 코어당 기준으로
쓰여 있었다고 판단해, **코어당 값을 판정 기준으로 삼는다.** 시스템 전체 값은 참고용으로
같이 남긴다.

### 1.4 펫이 실제로 떠 있고 실제로 애니메이션 중인지 확인

펫은 `Idle` 상태로 20초가 지나면 스스로 잠들어 렌더링을 완전히 멈춘다
(`PetWindow.SleepAfterTicks = Fps * 20`). 이 사실을 무시하고 긴 구간을 통으로 재면, 배회
구간과 잠듦 구간이 뒤섞여 실제보다 낮은(더 보기 좋은) CPU 수치가 나올 수 있다.

그래서 CPU는 세 구간으로 **의도적으로 분리**해서 쟀다.

1. **배회(wandering)** — 갓 기동한 펫을 20초 미만(정착 1.5초 + 워밍업 2초 + 12초 샘플
   = 15.5초 누적 유휴) 동안만 샘플링한다. 잠들 수 없다.
2. **잠듦(asleep)** — 유휴 10초를 추가로 대기해(누적 유휴 시간이 확실히 20초를 넘도록)
   확실히 잠든 뒤 10초 샘플링한다.
3. **활동중(working)** — 2초마다 `Read`/`Edit`/`Bash`/`Grep`을 순환시키며 `tool_use`
   이벤트를 트랜스크립트에 주입해 20초 잠듦 임계값을 절대 넘기지 않으면서 10초
   샘플링한다. 도구 이름을 하나로 고정하지 않은 이유는 §3에 남긴다.

각 구간이 끝날 때마다 `Get-Process`로 프로세스가 여전히 살아있는지(`HasExited`) 확인하고,
배회/활동중 CPU가 잠듦 CPU보다 뚜렷이 높은지 자동으로 검사해 그렇지 않으면
`[의심스러움]`을 출력하도록 했다. **1차 실행에서 실제로 이 검사가 걸렸고, 맹목적으로
통과 처리하지 않고 원인을 조사했다** — 조사 과정과 그 결과로 하네스 자체를 고친 내용을
§3에 전부 남긴다.

### 1.5 하네스가 통제하는 합성 세션 — 세션 하나만 살아있게

`SessionStart` 훅을 거치지 않는다. 대신 하네스가 직접 `${CLAUDE_PLUGIN_DATA}/sessions/`에
세션 레코드를 써서 등록한다. `pid`는 **PowerShell 자신의 PID**(`$PID`)와 그 정확한
`StartTime`을 쓴다 — `WindowsProcessProbe.IsAlive`는 PID 생존 + 시작 시각(±2초 허용)을
권위로 삼으므로, 스크립트가 살아있는 동안은 워치독이 펫을 절대 끄지 않는다.

지연 측정용 세션과 CPU 구간 측정용 세션은 서로 다른 트랜스크립트를 가리키는 별도
세션으로 등록하며, **지연 측정이 끝나면 그 세션을 바로 해제한 뒤에 CPU 구간용 세션을
새로 등록한다** — 두 세션이 동시에 등록된 채로 CPU 구간을 재면, 펫이 활동 없는 세션
하나를 추가로 추적하는 비용(세션 레지스트리 디렉터리 열거, 빈 트랜스크립트 파일 열기)이
"세션이 하나뿐인 상황"을 재려는 CPU 구간 측정치에 섞여 들어간다. 이건 최초 구현에는
없던 처리였고, §4의 자체 재검토에서 발견해 고친 뒤 전체를 다시 실행했다(§2가 그 결과다).

### 1.6 이름이 아니라 전체 경로로 우리 펫을 구분

이 머신에는 VS Code Python 확장(`ms-python.vscode-python-envs-...\python-env-tools\bin\pet.exe`)이
설치한, 이름만 같은 무관한 `pet.exe`가 실제로 떠 있다(측정 중 PID 10916으로 계속 확인됨).
`Get-OurPetProcess`는 `Get-Process -Name pet`으로 후보를 찾은 뒤 `$_.Path`가
`plugin/bin/pet.exe`의 **정규화된 전체 경로**와 대소문자 무시 일치하는 것만 골라낸다.
프로세스 이름만으로 찾거나 죽이는 코드는 스크립트 어디에도 없다.

### 1.7 워크로드 두 축

1. **파일 쓰기 지연** — 펫이 실제로 tail 하고 있는 바로 그 트랜스크립트 파일에
   `FileMode.Append` + `FileShare.ReadWrite|Delete`로 이어 쓴다. 스펙 §6.2("파일 잠금
   없음")가 실제로 지켜지는지, 진짜 공유 자원에 대해 최종 확인하는 워크로드다.
2. **CPU 바운드 연산 지연** — 트랜스크립트와 무관한 SHA-256 반복 해시. 파일 I/O가 전혀
   없는 순수 스케줄링 경합을 재, 스펙 §6.5("빌드·테스트와 CPU 경쟁하지 않음")를 파일
   축과 다른 방식으로 교차 검증하는 두 번째 축이다. 브리프에는 없던, 이번에 추가한
   워크로드 축이다.

### 1.8 정리

`try { ... } finally { ... }`로 본문 전체를 감쌌다. 중간 어디서 예외가 나도(펫이 안 뜬다,
프로세스가 갑자기 사라진다 등) `finally`가 등록한 세션 파일을 지우고, 우리 펫을
`Stop-Process`하고, 임시 디렉터리(`%TEMP%\pet-bench-<guid>\`)를 삭제한다. 측정이 끝난
지금 `Get-Process -Name pet`에는 무관한 VS Code pet.exe(PID 10916) 하나만 남아 있고,
`%TEMP%`에 `pet-bench-*`/`pet-diag-*` 디렉터리는 하나도 남지 않았다(육안 확인함).

## 3. `[의심스러움]` 조사 (1차 실행) — "활동중" CPU가 "잠듦" CPU보다 낮게 나온 이유

1차 실행에서는 하네스 자신이 이 결과를 의심스럽다고 표시했다. **그대로 보고하지 않고
조사했다.** 1차 실행의 해당 구간 원본 출력:

```
=== [1/3] 배회(Idle, 잠들기 전) — 12초 표본, 잠듦 임계값(20초) 미만 ===
  배회 CPU                       코어당=  3.382%   시스템전체= 0.2818%   (CPU 0.406s / 경과 12.01s)

=== [2/3] 잠듦(Asleep) — 유휴 10초 추가 대기 뒤 10초 표본 ===
  잠듦 CPU                       코어당=  1.249%   시스템전체= 0.1041%   (CPU 0.125s / 경과 10.01s)

=== [3/3] 활동중(Working) — 2초마다 tool_use 이벤트 주입, 10초 표본 ===
  활동중 CPU                      코어당=  0.777%   시스템전체= 0.0647%   (CPU 0.078s / 경과 10.05s)

[의심스러움] 활동중 CPU(0.777%)가 잠듦 CPU(1.249%)보다 뚜렷하게 높지 않습니다. 주입한 트랜스크립트 이벤트가 실제로 반영되고 있는지 재확인이 필요합니다.
```

### 3.1 가설 1 — 트랜스크립트 이벤트가 실제로 반영되지 않는다 (하네스 버그)

가장 먼저 의심한 것은 하네스 쪽 결함이었다. Windows PowerShell 5.1의 `Add-Content
-Encoding utf8`이 파일이 비어있을 때 첫 호출에서 UTF-8 BOM을 끼워 넣는다는 것을
직접 실험으로 확인했다(`bom-test.jsonl` 실험, 3번 호출 중 오프셋 0에 BOM 1개만 삽입 —
호출마다 삽입되지는 않음). 이 경우 트랜스크립트의 **첫** 이벤트 한 줄만 파싱에
실패할 수 있고, 이후 줄은 정상이다.

이 가설을 직접 배제하기 위해, 별도 진단 스크립트로 다음을 확인했다.

- 신선한 펫 프로세스에 5초 유휴 베이스라인을 재고,
- 이어서 200ms 간격으로 `Read`/`Edit`/`Bash`/`Grep`을 순환시키며 8초간 40개 이벤트를
  주입하고,
- 트랜스크립트 파일의 줄 수(40줄, 정확히 일치)와 마지막 줄 내용을 직접 확인했다.

결과:
```
baseline idle 5s: 0.4219s CPU   (약 8.4%)
heavy activity ~8s (40 events): 0.2656s CPU   (약 3.3%)
transcript line count: 40
last line: {"type":"assistant",...,"name":"Grep",...}
```

40개 이벤트가 전부 파일에 정확히 쓰였고, 활동 중 CPU(3.3%)가 완전한 0이 아니라 베이스라인
대비 뚜렷이 다른 값으로 나왔다. 즉 **이벤트는 정상적으로 도달하고 실제로 상태 머신에
반영된다.** "이벤트가 안 먹힌다"는 가설은 기각했다.

### 3.2 가설 2 — `PetHost`의 1초 폴링 자체가 "잠듦" 상태에서도 계속 도는 고정비용이다

`src/PetApp/PetHost.cs`를 다시 읽었다. `PetHost`는 자기 자신의 `DispatcherTimer`
(1초 간격)를 갖고 있고, 이 타이머는 **`PetWindow`의 애니메이션 잠듦 상태와 완전히
독립적으로 계속 돈다** — `PetHost.Start()`가 시작한 뒤로는 워치독이 종료를 결정하기
전까지 매초 `SessionRegistry.ReadAll()`(디렉터리 열거 + 세션 JSON 파일 읽기),
각 세션의 `TranscriptTail.ReadNew()`(파일 열기 + 읽기), `DrainNotifications()`(디렉터리
열거)를 실행한다. `PetWindow.Tick()`의 20초 잠듦 조기 반환(`SleepAfterTicks`)은
`PetWindow`의 12fps 렌더 타이머에만 적용되고, `PetHost`의 1Hz 폴링에는 전혀 적용되지
않는다.

이것이 1차 실측과 정확히 들어맞는다.

- **잠듦(1.249%)** 구간에서도 렌더링은 완전히 멈췄지만, `PetHost`의 1초 폴링(세션
  디렉터리 열거 + 트랜스크립트 읽기 시도)은 계속 돈다 — 그래서 잠듦 CPU가 정확히
  0%가 아니라 1% 남짓의 바닥값을 갖는다. (참고로 이 값은 1차·2차 실행에서 코어당
  1.249%로 **완전히 동일하게** 재현됐다 — `CPU 0.125s / 경과 10.01s`까지 일치한다.
  Windows 프로세스 CPU 계정이 고정된 양자 단위로 집계되는 만큼, 항상 같은 파일 I/O
  작업을 매초 반복하는 이 폴링 비용이 매우 결정적이라는 근거로 본다.)
- **활동중** 구간은 같은 1Hz 폴링 비용 위에, `Reading`/`Writing` 상태(도구
  `Read`/`Grep`→Reading, `Edit`→Writing)의 **제자리** 애니메이션(위치 이동 없음, 스프라이트
  재대입도 프레임이 실제로 바뀔 때만) 비용이 얹힌다. `PetWindow.Tick()`의 주석대로
  "시트 안에는 열이 달라도 그림이 같은 프레임이 섞여 있다"(같은 비트맵 인스턴스로
  캐시됨)이고, 정지 상태는 `SetWindowPos` 자체를 호출하지 않는다 — 그래서 이 추가
  비용은 설계상 작다.
- **배회** 구간은 `Idle` 상태로 2틱(6Hz)마다 실제로 위치가 바뀌어 `SetWindowPos`와
  레이어드 윈도우 재합성이 반복적으로 발생한다 — 세 구간 중 가장 비싼 이유가 정확히
  설계 문서 §6.5/PetWindow.cs의 주석이 말하는 그 지점(위치 이동 = 재합성 비용)과 일치한다.

즉 1차 실행에서 "활동중이 잠듦보다 낮다"는 관측은, **두 구간이 거의 같은 고정비용
(1Hz 세션 폴링)에 지배되고, 그 위에 얹히는 활동중의 한계 비용(제자리 스프라이트 갱신)이
측정 잡음보다 작기 때문**이라고 결론지었다. 8~10초짜리 표본에서 1% 안팎의 값끼리 순서가
뒤집히는 것은 이 설명과 모순되지 않는다.

### 3.3 발견한 진짜 결함과 그 수정

가설 2를 확인하는 과정에서, CPU 구간 측정 시작 시점에 **지연 측정용 세션이 아직
등록 해제되지 않은 채로 남아있다는 것**을 발견했다(§1.5) — CPU 구간에서 재려는
"세션 하나"가 실제로는 "세션 둘(활동 없는 지연-측정 세션 + 방금 등록한 CPU 측정
세션)"이 됐다는 뜻이다. 이건 활동중 구간의 정확한 절대값을 왜곡할 뿐 "이벤트가
반영되는가"라는 §3.1의 질문과는 무관하지만, CPU 구간 측정 전체의 대표성을 해치는
결함이라 판단해 고쳤다(`Unregister-SyntheticSession`을 CPU 구간 시작 **전에** 호출).

수정 후 전체를 재실행한 결과(§2)가 이 문서의 최종 수치다 — 활동중(2.016%)이 잠듦
(1.249%)과 배회(2.733%) 사이에 자연스럽게 놓였고, 하네스의 자동 검사도 더 이상
`[의심스러움]`을 내지 않았다.

### 3.4 배회 CPU의 재현성 확인

"미달" 판정의 근거가 되는 배회 CPU 수치 자체가 튀는 값(outlier)인지 확인하기 위해,
1차·2차 전체 실행 외에 동일한 프로토콜(정착 1.5초 + 워밍업 2초 + 12초 샘플)로 **별도
실행 2회**를 추가로 반복했다.

```
trial 1: 코어당=4.553%  시스템전체=0.3794%  (CPU 0.547s / 12.01s)
trial 2: 코어당=3.255%  시스템전체=0.2713%  (CPU 0.391s / 12.00s)
```

전체 4회(1차 3.382%, 2차 2.733%, 추가 4.553%/3.255%) 모두 **2.73%~4.55%** 범위에
있다 — 전부 1% 기준을 넉넉히(2.7배~4.6배) 초과하며, 튀는 값 하나로 미달 판정을 내린
것이 아니다.

### 3.5 결론

이 조사로 세 가지가 분명해졌다.

1. `[의심스러움]` 경고는 순수한 버그가 아니라 **실제 설계 특성**(1Hz 폴링이 잠듦
   상태에서도 계속 돈다)을 정확히 짚어냈다 — 하네스가 스스로 문제를 찾아냈고, 코드로
   원인을 추적해 설명할 수 있었다.
2. 그 조사 과정에서 하네스 자신의 **진짜 결함**(CPU 구간에 세션이 중복 등록됨)도
   함께 발견해 고쳤다 — "의심스러운 결과는 조사한다"는 원칙이 실제로 결함을 잡아낸
   사례다.
3. **배회(Idle 상태에서의 반복적인 위치 이동) 쪽이 유휴 CPU 기준 미달의 실제 원인이다.**
   "잠듦"이나 "활동중(대부분 제자리 애니메이션)"은 1~2% 안팎이라 기준에 훨씬 가깝지만,
   스펙이 실제로 재라고 요구하는 것 — 그리고 이전에 기록된 "배회 중 2.21%"가 가리키던
   바로 그 상태 — 는 네 번의 독립 측정 모두에서 기준을 넘었다.

## 4. 기준별 판정

### 4.1 쓰기 지연 중앙값 차이 — **통과**

- 최종 실측: ON-OFF = -0.0005 ms
- 조건 내부 블록간 중앙값 변동폭(OFF 0.0012ms, ON 0.0013ms)이 조건 간 차이(0.0005ms)의
  2배 이상이다.
- **가장 강한 근거는 재현 자체다**: 1차 실행에서는 +0.0003ms, 2차(최종) 실행에서는
  -0.0005ms — 부호가 실제로 뒤집혔다. 브리프가 요구한 통과 기준("재실행 시 부호가
  뒤집힐 정도")을 추정이 아니라 직접 관측했다.
- 추가로 CPU 바운드 연산 지연(두 번째 워크로드 축)도 같은 패턴이다: 최종 실행 중앙값
  차이 +0.0006ms로 사실상 0.

### 4.2 P99 차이 — **통과**

- 파일 쓰기: ON-OFF = -0.0008 ms (< 1 ms, 부호도 음수 — ON이 더 빠르게 나왔다)
- CPU 바운드 연산: ON-OFF = -0.0092 ms (< 1 ms)
- 두 워크로드 모두 극단값(max)에는 이상치가 하나씩 있다(예: OFF 파일 쓰기 max
  2.107ms, CPU 연산 OFF max 1.578ms) — 하지만 이건 P99 자체가 아니라 2000개 표본 중
  1~2개의 단발성 값이다. 이런 이상치가 OFF와 ON 양쪽 모두에서(어느 한쪽에 쏠리지
  않고) 관찰됐다는 것 자체가, 이게 펫이 아니라 파일시스템/디스크 스케줄러 수준의
  일반적인 잡음이라는 근거를 보탠다. P99(2000개 중 상위 20번째)는 이 이상치들의
  영향을 받지 않는다.

### 4.3 유휴(배회) CPU — **미달**

- 기준: 1% 미만 (코어당)
- 실측: **2.733%** (최종 실행), 4회 재현 평균 약 **3.48%** (2.73%~4.55%)
- 시스템 전체 기준으로는 0.2278%(최종 실행) — 하지만 이 문서는 §1.3에서 밝힌 이유로
  코어당 값을 기준으로 판정한다. 스펙 문구가 "유휴 CPU 1% 미만"이라고만 쓰고 정규화
  기준을 명시하지 않았으므로, 더 보수적인(더 엄격한) 코어당 기준으로 판정하는 것이
  "기준을 낮추지 않는다"는 이 태스크의 원칙에 맞다.
- **Task 12(BelowNormal 우선순위 적용) 이후에도 미달이다.** 참고로 이전에 기록된
  "배회 중 2.21%"와 비교하면 이번 4회 측정(2.73%~4.55%)의 하한이 오히려 그보다 높다.
  두 수치는 서로 다른 시점·다른 배경 부하에서 측정된 것이라 직접 비교는 조심스럽지만,
  적어도 "BelowNormal 덕분에 1% 밑으로 내려갔다"는 근거는 이번 측정 어디에도 없다.
  BelowNormal 우선순위는 다른 프로세스와의 CPU 스케줄링 **경합**을 줄이는 것이지,
  펫 자신이 배회하며 반복적으로 창을 재배치하고 레이어드 윈도우를 재합성하는
  **절대적인 작업량**을 줄이지는 않는다.
- §3.2에서 밝혔듯, 이 비용의 실제 원인은 `Idle` 상태의 반복적인 위치 이동(6Hz
  `SetWindowPos` + 레이어드 윈도우 소프트웨어 재합성)이다. `AllowsTransparency`가
  강제하는 소프트웨어 재합성 비용이며, Task 13 브리프에 앞서 미리 알려진 원인
  ("남은 비용은 AllowsTransparency가 강제하는 레이어드 윈도우 소프트웨어 재합성")과
  정확히 일치한다.

## 5. 이 측정이 말하지 않는 것 (한계)

- **"잠듦"과 "활동중(대부분 제자리 애니메이션)" 상태는 유휴 CPU 기준에 훨씬 가깝다**
  (각각 1.249%, 2.016% — 여전히 기준을 넘지만 배회의 절반 이하다). 즉 코딩 세션 중
  펫이 도구 호출에 반응해 제자리에서 Reading/Writing 애니메이션만 재생하는 동안에는
  CPU 비용이 배회 상태보다 뚜렷이 낮다. 기준 미달 폭이 가장 큰 것은 **활동 없이 20초
  미만 동안 화면을 배회하는** 상태다. 이 상태는 사람이 프롬프트를 입력하는 동안이나
  Claude Code의 사고(thinking) 구간처럼, 정확히 "사람이 코딩 자체를 하고 있지는 않은"
  순간에 가장 흔하다 — 그렇다고 기준 미달이 정당화되지는 않는다. 스펙은 상태를 가리지
  않고 "유휴 CPU 1% 미만"이라고 못박았다.
- CPU 구간 측정은 각 12초/10초짜리 표본이다(배회는 재현 확인으로 총 4표본). 초 단위
  짧은 창에서 `TotalProcessorTime`은 Windows의 프로세스 CPU 계정 방식에 따른 양자화
  잡음을 포함한다. 그럼에도 배회 4회 표본이 모두 1% 기준을 뚜렷이(2.7배 이상) 초과했고
  잠듦 CPU는 두 전체 실행에서 소수점 셋째 자리까지 동일하게 재현됐으므로("코어당
  1.249%", §3.2), 측정 자체의 잡음이 "미달"이라는 결론을 뒤집을 가능성은 낮다고 판단한다.
- 이 머신에서 측정한 값이며, 다른 하드웨어(특히 GPU 합성 경로가 다른 머신)에서는 배회
  CPU 수치가 달라질 수 있다.
- 쓰기 지연 측정은 트랜스크립트가 아직 작을 때(테스트 세션 기준 최대 수백 KB)의
  값이다. 매우 긴 세션에서 트랜스크립트가 수십 MB로 자란 뒤에도 `TranscriptTail`이
  증분 읽기만 하므로(`SkipToEnd`의 64KB 창 제한) 이 결론이 유지될 것으로 보이지만,
  이번 측정은 그 시나리오를 직접 재지는 않았다.

## 6. 후속 조치가 필요한 항목

**유휴(배회) CPU 기준 미달은 "원인을 찾아 고친 뒤 재측정한다"는 브리프의 원칙에 따라
해결되어야 하지만, 원인 규명 자체는 이번 태스크(측정)의 범위를 넘는 `src/PetApp/` 구현
변경을 요구한다** — 이 태스크는 `src/`, `tests/`를 건드리지 않기로 고정되어 있다. 이
문서는 원인을 정확히 지목하는 데까지만 하고, 고치는 것은 별도 태스크로 남긴다.

원인(§3.2, §4.3): `Idle`(배회) 상태에서 6Hz로 반복되는 위치 이동이 `AllowsTransparency`
레이어드 윈도우의 소프트웨어 재합성을 그만큼 반복시킨다. 가능한 개선 방향(구현하지
않음, 제안만):

- 배회 이동 속도를 낮추거나 재배치 주기를 6Hz보다 더 낮춰, 초당 재합성 횟수 자체를
  줄인다 (체감 속도 저하와 맞바꿈).
- `AllowsTransparency` 대신 `UpdateLayeredWindow` 직접 호출 등 더 가벼운 투명 창 갱신
  경로로 교체한다 (스펙 §11이 "구현 초반에 확인할 것"으로 남겼던 "투명 최상위 창의
  실제 렌더링 품질" 항목과 연결된, 더 근본적인 변경).
- 배회 자체를 더 드물게(예: 완전히 멈춰있다가 가끔만 짧게 이동) 만들어 위치 변경
  이벤트 수를 줄인다.
- `PetHost`의 1초 폴링(§3.2) 자체도 "잠듦"/"활동중" 상태의 바닥값(1.2~2%)을 만드는
  요인이다. 배회만큼 크지는 않지만, 세션이 여러 개 등록될수록 이 비용은 세션 수에
  비례해 커질 수 있다 — 다중 세션 환경에서의 재측정도 후속 후보다.
